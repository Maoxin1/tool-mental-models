# Codex CLI：把“写代码”重构为“受约束的委托”

> 这不是安装指南、命令手册或参数速查表。
>
> 默认前提：AI 负责绝大多数具体操作；人负责定义目标、事实来源、权限边界、验收证据与最终责任。
>
> 文档状态：依据 OpenAI 官方资料于 2026-08-02 核对；本机参考版本为 codex-cli 0.146.0。具体名称和默认值会变化，文中的心智模型应比它们更长寿。

---

## 先给结论：最重要的“参数”不是旗标，而是 10 个控制变量

把 Codex CLI 想成一名能看代码、改文件、运行工具并根据结果继续行动的代理。真正决定一次委托是否可靠的，不是记住多少选项，而是下面十个控制变量。

| 优先级 | 控制变量 | 你真正要决定的问题 | 当前实现中的概念锚点 |
|---:|---|---|---|
| 1 | 任务契约（Task Contract） | 期望结果是什么？什么算完成？什么不能改变？ | 初始任务描述与后续纠偏 |
| 2 | 工作边界（Workspace Scope） | 哪个目录、仓库、分支和对象属于本次任务？ | 工作目录、附加目录 |
| 3 | 能力边界（Sandbox） | Codex 在技术上能读、写、执行和联网到哪里？ | read-only、workspace-write、danger-full-access |
| 4 | 干预策略（Approval Policy） | 何时必须停下来，由人或审查策略决定是否越界？ | untrusted、on-request、never、审批审查者 |
| 5 | 认知配置（Model & Reasoning） | 任务需要怎样的质量、速度、成本和推理深度？ | 模型、reasoning effort、服务层级 |
| 6 | 世界输入（Context） | Codex 能看到哪些代码、图像、规则、历史和外部事实？ | 会话、图像、AGENTS.md、搜索、连接的数据源 |
| 7 | 行动能力（Tools & Network） | 它能调用哪些本地工具、MCP、插件、连接器和网络目的地？ | Shell、MCP、plugins、web search、网络策略 |
| 8 | 执行拓扑（Execution Topology） | 工作应在本机还是云端、交互还是非交互、单次还是持续会话中发生？ | CLI、exec、review、resume、cloud |
| 9 | 规则寿命（Instruction Lifetime） | 约束只适用于这次任务、这个仓库、个人默认，还是组织强制策略？ | Prompt、AGENTS.md、项目/用户配置、profile、managed requirements |
| 10 | 证据契约（Evidence Contract） | 用哪些独立证据证明结果正确，并让下游可靠消费？ | Diff、测试、静态检查、审查、JSONL、结构化输出 |

最容易被高估的是“选哪个模型”；最容易被低估的是：

> **范围、权限、事实来源和验收证据。**

模型决定“它可能想得多好”；范围与权限决定“它最多能影响什么”；上下文决定“它基于什么世界行动”；证据决定“你凭什么相信任务完成”。

当前官方 CLI 参考把模型、工作目录、沙箱、审批、搜索、配置覆盖与不同执行形态暴露为可配置入口；但这些名称只是上述控制变量在某个版本中的实现。[Codex CLI 概览](https://developers.openai.com/codex/cli/features) · [CLI 参考](https://developers.openai.com/codex/cli/reference)

最小循环是：

> **意图 → 观察 → 计划 → 行动 → 读取反馈 → 验证 → 继续、纠偏或停止**

Codex 的价值来自整个闭环，而不只是中间那一步“生成代码”。

## 1. 本质（Essence）

### 一句话定义

**Codex CLI 是一个终端优先的编码代理运行时：它把高层目标放进一个受上下文、工具、权限和验证约束的反馈循环，在真实开发环境中推进软件状态变化。**

### 为什么它存在？

软件工作很少只是“写出一段文本”。一个真实变更通常需要：

- 找到相关代码与真实依赖；
- 理解局部修改对全局行为的影响；
- 选择并执行编辑、构建、测试、搜索和版本控制工具；
- 根据错误与新证据改变计划；
- 控制修改范围和外部副作用；
- 最后交付可审查的差异与验证证据。

普通语言模型可以提出代码；传统脚本可以执行预先写好的固定步骤。两者之间缺少的是：

> **面对不完整信息，能观察环境、选择下一步、执行并根据反馈自我修正的受控代理循环。**

Codex CLI 因此不是“更聪明的文本框”，也不只是“会写代码的命令”。它是自然语言意图与真实开发环境之间的控制层。

### 它解决的根本问题

根本问题不是“怎样少敲几行代码”，而是：

> **怎样把一项只有目标、没有完整步骤的软件任务，委托给 AI，同时限制它的能力半径，并获得足以判断结果的证据？**

这包含四个彼此独立的问题：

1. **认知问题**：任务与代码库究竟意味着什么？
2. **行动问题**：下一步应该调用什么工具，改变什么状态？
3. **治理问题**：哪些行动被允许，哪些越界需要审批？
4. **认识论问题**：怎样知道结果真的正确，而不只是看起来合理？

### 没有它时，人们通常怎么办？

- 人工浏览代码、编辑文件、运行命令，再根据结果反复调整；
- 用自动补全或聊天模型处理局部片段，再由人手工把答案搬进环境；
- 为已知流程编写脚本，但遇到异常分支仍由人接管；
- 在 IDE、终端、浏览器、工单和文档之间来回传递上下文；
- 把复杂工作拆成详细操作说明，再让执行者逐步照做。

这些方式仍然有价值，但共同成本是：**人承担了大量上下文搬运、步骤选择和反馈闭环维护。**

### 它带来的新可能

- 人描述期望状态，AI 自己发现大部分具体路径；
- 一次任务不再等于一次回答，而是一个可持续纠偏的工作线程；
- 将本地工具、代码库知识和外部系统纳入同一行动循环；
- 把团队规范从口头习惯沉淀为可继承的规则、技能与策略；
- 在隔离环境中并行尝试多个任务或多个方案；
- 让“结果 + 证据”成为默认交付物，而不是只交付一段代码；
- 把人的工作重心从“操作员”迁移为“问题定义者、边界设计者、审查者与责任人”。

### 三个必须保持的区分

#### 模型不等于代理

模型负责推理与生成；代理还包含上下文装配、工具调用、状态观察、循环控制、权限与会话。更强的模型不会自动带来更正确的工作边界。

#### 能力不等于授权

工具或沙箱决定 Codex 技术上能做什么；组织政策、任务边界和人的授权决定它应该做什么。

#### 回答不等于结果

自然语言总结是声明；Diff、测试、系统状态和独立审查才是证据。官方资料也将 CLI 定义为能在本地仓库中检查、编辑并运行工具的工作界面，而不仅是回答问题。[Codex CLI](https://developers.openai.com/codex/cli/features)

## 2. 世界模型（World Model）

### 2.1 Codex 在现实系统中的位置

~~~mermaid

    end

    subgraph Runtime[Codex 代理运行时]

    end

    subgraph Execution[执行环境]

        Shell[Shell 与本地开发工具]
~~~

Codex 位于“人的意图”和“可执行系统”之间，但它不是中立管道。它会推断、选择、尝试和纠错，因此必须同时设计它的**信息边界**与**行动边界**。

### 2.2 它处理哪些对象（Objects）

| 对象类别 | 典型对象 | Codex 对它做什么 | 最终事实来源 |
|---|---|---|---|
| 意图对象 | 目标、约束、验收条件、停止条件 | 解释、分解、持续对齐 | 任务负责人 |
| 知识对象 | 代码、文档、AGENTS.md、图片、历史消息、网页 | 读取、关联、压缩、推断 | 原始来源与当前版本 |
| 软件对象 | 文件、模块、依赖、配置、测试、构建产物 | 检查、创建、修改、删除、运行 | 工作区和版本控制 |
| 执行对象 | 命令、进程、终端、工具调用、网络请求 | 启动、观察、终止、重试 | 操作系统或远程系统 |
| 协作对象 | Issue、PR、评论、设计、工单、消息 | 查询、草拟、更新或提交 | 对应外部系统 |
| 证据对象 | Diff、测试结果、日志、审查发现、结构化输出 | 汇总、比较、解释 | 生成证据的独立机制 |
| 会话对象 | 线程、上下文窗口、压缩摘要、目标状态 | 累积、压缩、恢复、分叉 | 会话记录与当前活动状态 |

### 2.3 涉及哪些角色（Actors）

| 角色 | 核心责任 | 不应被偷偷转移的责任 |
|---|---|---|
| 任务负责人 | 定义结果、边界、优先级和验收 | 对业务后果与最终采用负责 |
| Codex 代理 | 探索、规划、执行、反馈、修正 | 不能自行创造超出授权的新目标 |
| 模型 | 推理、生成候选行动与解释 | 不拥有真实系统状态，也不提供最终授权 |
| 沙箱 / 操作系统 | 强制执行技术能力边界 | 不判断业务上是否应该执行 |
| 审批者 / 自动审查策略 | 判断特定越界行动是否允许 | 不代替最终结果验收 |
| 工具与 MCP 服务 | 提供领域动作和数据 | 工具可用不代表工具输出绝对可信 |
| Git、测试、CI、审查者 | 保存差异、验证行为、暴露回归 | 不能弥补错误或缺失的产品目标 |
| 管理员 / 安全团队 | 设定组织不可绕过的约束 | 不替代项目级风险判断 |

### 2.4 管理哪些状态变化（State）

一次 Codex 任务至少同时推进五条状态线：

~~~mermaid
stateDiagram-v2
    [*] --> GoalUnknown: 目标模糊
    GoalUnknown --> GoalBounded: 目标、范围与验收明确

    [*] --> ContextSparse: 上下文不足
    ContextSparse --> ContextUseful: 找到相关代码、规则与事实

    [*] --> RepoS0: 仓库状态 S0
    RepoS0 --> RepoChanged: 候选修改
    RepoChanged --> RepoVerified: 验证通过
    RepoChanged --> RepoRevised: 验证失败或证据不足
    RepoRevised --> RepoChanged

    [*] --> AuthorityDefault: 默认权限
    AuthorityDefault --> AuthorityGranted: 在策略内自动行动
    AuthorityDefault --> ApprovalPending: 需要越界
    ApprovalPending --> AuthorityGranted: 获批
    ApprovalPending --> AuthorityDenied: 拒绝

    [*] --> ConfidenceClaim: AI 声称完成
    ConfidenceClaim --> EvidenceChecked: 独立证据被检查
    EvidenceChecked --> Accepted: 人或下游接受
~~~

关键点：**“代理停止运行”“代理说完成”“测试通过”“任务被接受”是四个不同状态。**

### 2.5 改变哪些工作流（Workflow）

传统工作流的主循环在人脑中：

> 人观察 → 人决定 → 人操作 → 人读取反馈 → 人修正

Codex 工作流把中间循环交给代理：

> 人定义任务契约 → Codex 执行多轮观察与行动 → 人在关键边界介入 → 系统产出证据 → 人验收

变化不是“人消失”，而是人的介入点改变：

- 从每一步操作，移动到任务开始时的边界设计；
- 从持续盯着过程，移动到异常、越界和决策点；
- 从检查 AI 是否“努力过”，移动到检查证据是否满足验收；
- 从把个人经验藏在脑中，移动到把规则沉淀为仓库与组织资产。

### 2.6 与哪些系统交互（Systems）

- **本地计算系统**：文件系统、Shell、编译器、包管理器、测试器、数据库和容器；
- **软件协作系统**：Git、代码托管、Issue、PR、CI、发布流水线；
- **知识系统**：仓库文档、官方文档、Web 搜索、连接的数据源；
- **工具协议**：MCP、插件和应用连接器，把外部数据与动作引入代理；
- **策略系统**：沙箱、审批、规则、Hooks、组织强制配置；
- **云执行系统**：隔离容器、可复现环境、后台和并行任务。

MCP 的生态位置是“把模型接到工具和上下文”，不是另一个模型；Skills 的位置是“封装可重复工作方法”，不是额外权限；Cloud 的位置是“改变执行地点、隔离和并行方式”，不是改变目标责任。[MCP](https://learn.chatgpt.com/docs/extend/mcp) · [Skills](https://developers.openai.com/codex/skills) · [Codex Cloud](https://developers.openai.com/codex/cloud)

### 2.7 创造哪些价值（Value）

Codex 最重要的价值不是单位时间生成多少代码，而是降低三类成本：

1. **协调成本**：人不必为 AI 预先写出全部步骤；
2. **切换成本**：探索、修改、运行和反馈可留在同一工作线程；
3. **异常处理成本**：代理可以根据失败自行尝试合理修正。

它同时提高两种杠杆：

- **适应性杠杆**：面对未知路径时仍能推进；
- **并行性杠杆**：把多个独立任务放入不同线程或环境。

但价值只有在风险受控时才成立：

> **净价值 ≈ 可验证的任务吞吐 × 复用程度 − 错误爆炸半径 − 审查与返工成本**

### 3.2 重要概念：名词、动词、目的与关系

| 名词（Entity） | 动词（Action） | 目的（Purpose） | 与其他概念的关系（Relationship） |
|---|---|---|---|
| 目标（Goal） | 指定期望变化 | 给行动方向 | 被范围和约束限制，由验收标准判断 |
| 任务契约（Task Contract） | 对齐目标、边界与证据 | 降低委托歧义 | 连接人类意图与代理循环 |
| 范围（Scope） | 纳入或排除对象 | 限制工作集与爆炸半径 | 映射到工作目录、仓库、分支和附加资源 |
| 代理（Agent） | 观察、计划、行动、修正 | 在步骤未知时推进目标 | 使用模型思考，使用工具行动，受策略约束 |
| 模型（Model） | 推理、生成、评估候选 | 提供认知能力 | 是代理的组件，不拥有工具权限或事实状态 |
| 上下文（Context） | 提供任务相关信息 | 改善判断与局部一致性 | 来自提示、代码、规则、会话、工具和外部来源 |
| 会话（Session） | 保存连续工作状态 | 支持多轮纠偏与恢复 | 上下文会增长、压缩、分叉或过期 |
| 工作区（Workspace） | 承载本地任务对象 | 定义主要读写边界 | 是沙箱和版本控制的关键边界 |
| 沙箱（Sandbox） | 技术性允许或阻止 | 限制文件、进程与网络能力 | 回答“能不能做”，与审批策略正交 |
| 审批策略（Approval Policy） | 暂停、询问、允许或拒绝 | 控制何时需要外部判断 | 回答“什么时候必须问”，不能扩大沙箱本身 |
| 网络策略（Network Policy） | 限制外部目的地 | 控制开放世界访问 | 同时影响信息新鲜度、供应链与数据泄露风险 |
| 工具（Tool） | 查询或改变系统 | 把推理落到现实 | Shell、MCP、连接器都属于能力接口 |
| Skill | 封装可重复方法 | 让代理可靠复用工作流 | 提供过程知识，可含脚本，但不自动授予权限 |
| Plugin | 分发技能与连接能力 | 让能力可安装、可共享 | 可打包 Skills、MCP、Hooks 和资源 |
| AGENTS.md | 继承项目指导 | 固化仓库约定 | 比一次性提示长寿，按目录层级覆盖 |
| 配置（Config） | 设定运行默认与策略 | 控制代理如何运行 | 与任务指导不同；存在用户、项目、组织优先级 |
| Hook | 在生命周期事件上执行规则 | 机械化检查或治理 | 围绕工具和会话边界触发，不替代任务目标 |
| Diff | 表示候选状态变化 | 让修改可比较、审查、回滚 | 是产物证据之一，不证明行为正确 |
| 测试 / 检查（Checks） | 验证可观察性质 | 对候选修改施加断言 | 是独立反馈，但覆盖范围决定证明力度 |
| 审查（Review） | 从不同视角找风险 | 降低单一路径盲点 | 应独立于原始生成过程，仍需明确审查范围 |
| 结构化输出（Structured Output） | 固定结果形状 | 支持机器下游 | 解决“能否解析”，不自动解决“内容是否正确” |
| 云环境（Cloud Environment） | 隔离并承载任务 | 提供后台、并行和复现 | 改变执行拓扑；仍需环境定义、网络和验收 |

### 3.3 六组关键关系

#### 目标 → 计划 → 动作

目标描述结果；计划是假设；动作改变现实。计划可以重写，目标不应在未授权时悄悄漂移。

#### 上下文 → 判断，但不等于事实

上下文是代理当前能看到的世界切片。它可能缺失、陈旧、被污染或在压缩中丢失。事实仍应回到源系统核对。

#### 沙箱 × 审批：两个正交轴

官方文档明确将安全控制拆成两层：沙箱限定技术能力，审批策略决定何时暂停询问。[Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)

| | 审批少 | 审批多 |
|---|---|---|
| 权限窄 | 流畅且爆炸半径小，适合常规本地任务 | 谨慎但可能频繁中断 |
| 权限宽 | 高吞吐也高风险，只适合外部已充分隔离的环境 | 能处理越界任务，但审查负担高 |

因此“从不询问”不等于“无限权限”；“每次询问”也不等于“技术上安全”。

#### 工具可用 → 能行动，但不等于被授权

连接 GitHub、浏览器或数据库只说明代理有一条路径。是否应调用、能否写入、谁批准和如何审计仍是独立问题。

#### Diff → 可见变化；测试 → 行为证据；验收 → 业务判断

三者不能互相替代。漂亮的 Diff 可能行为错误；测试通过可能不覆盖真正需求；业务接受也不应掩盖安全或合规失败。

#### 一次性提示 → 项目规则 → 可复用 Skill → 组织策略

这是“规则寿命与强制力”的梯度：

~~~mermaid
flowchart LR
    Prompt[一次性提示<br/>当前任务] --> AG[AGENTS.md<br/>仓库惯例]
    AG --> Skill[Skill<br/>可复用工作流]
    Skill --> Plugin[Plugin<br/>可分发能力包]
    Plugin --> Managed[Managed Requirements<br/>组织不可绕过约束]
~~~

不要把所有要求都塞进同一层：临时目标不应变成全局默认，合规底线也不应只靠提示词提醒。

## 4. 决策地图（Decision Map）

专业人士会在“需要把模糊软件目标交给一个能直接行动的系统”时想到 Codex，而不是在任何与代码有关的问题上都想到它。

### 4.1 总体决策树

~~~mermaid
flowchart TD
    S[出现一项软件工作] --> Q1{需要改变或检查<br/>真实代码与环境吗？}
    Q1 -->|否| Chat[普通对话、文档工具<br/>或确定性分析可能足够]
    Q1 -->|是| Q2{路径是否完全已知且稳定？}
    Q2 -->|是| Script[优先复用测试、脚本或 CI<br/>必要时让 Codex维护它]
    Q2 -->|否| Q3{需要本机上下文和即时纠偏吗？}
    Q3 -->|是| Local[本地交互式 Codex]
    Q3 -->|否| Q4{需要后台、隔离或并行吗？}
    Q4 -->|是| Cloud[云环境中的 Codex]
    Q4 -->|否| Local
    Local & Cloud --> Q5{风险或不确定性高吗？}
    Q5 -->|是| Guard[缩小范围、只读探索、独立审查<br/>明确审批与恢复路径]
    Q5 -->|否| Auto[在最小足够权限内自主执行]
    Guard & Auto --> Q6{结果由机器继续消费吗？}
    Q6 -->|是| Schema[结构化证据与失败语义]
    Q6 -->|否| Review[Diff、检查结果与人类验收]
~~~

### 4.2 真实工作场景

#### 场景 A：陌生代码库中的定位与小改动

**Situation**  
需求明确，但不知道代码在哪、依赖关系怎样、应该运行哪些检查。  
↓  
**Decision**  
使用本地交互式代理，把仓库作为工作边界，允许只读探索后在工作区内修改。  
↓  
**Reason**  
路径未知，需要“观察—行动—反馈”循环；纯脚本要求事先知道步骤。  
↓  
**Expected Outcome**  
得到范围受控的修改、解释过的影响面和与仓库匹配的验证证据。

#### 场景 B：高风险重构或安全敏感变更

**Situation**  
修改横跨核心模块，失败后果大，测试覆盖可能不足。  
↓  
**Decision**  
先把 Codex 当作只读调查员和方案比较者，再分阶段授权；生成者与审查者使用分离的任务上下文。  
↓  
**Reason**  
早期最大风险是理解错误，而不是执行速度；独立视角能减少同一推理链的盲点。  
↓  
**Expected Outcome**  
风险、依赖和迁移路径先显性化，修改批次更小，回滚与审查更可行。

#### 场景 C：重复的 CI 分析或报告

**Situation**  
任务会在无人值守环境反复运行，输出还要被其他程序处理。  
↓  
**Decision**  
采用非交互执行，固定最小权限、输入来源、结构化输出和失败条件。  
↓  
**Reason**  
机器下游需要稳定契约；交互式自由度会变成自动化不确定性。  
↓  
**Expected Outcome**  
流程可重放、可监控、可失败关闭，下游不依赖自然语言猜测。

官方非交互模式把进度与最终输出分流，并支持 JSONL 与模式约束；其生态意义是让 Codex 从“人的协作者”变成“流水线中的可观察组件”。[Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)

#### 场景 D：长时间、可并行的独立任务

**Situation**  
多个任务不需要持续占用本机，或需要彼此隔离的环境。  
↓  
**Decision**  
使用云执行，把每个任务绑定到可复现环境和明确代码基线。  
↓  
**Reason**  
并行能力来自环境隔离与任务独立，而不是让一个会话同时混合所有目标。  
↓  
**Expected Outcome**  
本机不被占用，各任务产生独立可审查结果，失败不会相互污染。

#### 场景 E：任务依赖 GitHub、设计稿、浏览器或内部数据

**Situation**  
仅凭本地仓库无法得到真实上下文或完成目标。  
↓  
**Decision**  
引入最小必要的 MCP、插件或连接器，只开放相关工具和动作权限。  
↓  
**Reason**  
代理的上限由可观察世界和可用执行器共同决定；但每个连接也扩大信任边界。  
↓  
**Expected Outcome**  
减少人工搬运上下文，同时保持数据来源、动作范围和审批点可追踪。

#### 场景 F：生产环境、合规数据或共享基础设施

**Situation**  
错误会影响真实用户、敏感数据或多人共享资源。  
↓  
**Decision**  
把本地代理限制在分析、补丁与可审查提案；真实变更通过受治理的发布系统和组织强制策略。  
↓  
**Reason**  
开发代理擅长提出与验证候选变化，但生产授权需要身份分离、审计和不可绕过控制。  
↓  
**Expected Outcome**  
Codex 提升分析与修复速度，而不成为绕开现有治理的侧门。

#### 场景 G：需求本身仍在形成

**Situation**  
不同方案对应不同产品取舍，尚未确定应优化什么。  
↓  
**Decision**  
先用 Codex 调查事实、构建原型或比较方案，不授权它替你决定产品目标。  
↓  
**Reason**  
代理可以优化已给定目标，却不能凭技术便利性创造正确的商业价值判断。  
↓  
**Expected Outcome**  
决策获得更好证据，但价值取舍仍由责任人完成。

#### 场景 H：已有稳定、确定性的自动化

**Situation**  
输入输出固定，异常空间小，现有脚本快速可靠。  
↓  
**Decision**  
继续使用脚本或 CI；让 Codex负责解释失败、维护脚本或处理例外，而不是替换确定性核心。  
↓  
**Reason**  
不确定代理不应取代更便宜、更快、更可证明的确定性程序。  
↓  
**Expected Outcome**  
稳定路径保持简单，AI 只用在需要判断与适应的部分。

#### 场景 I：只需要一个知识答案

**Situation**  
不需要访问真实仓库、运行工具或产生可验证状态变化。  
↓  
**Decision**  
优先普通对话或文档检索，不必启动编码代理。  
↓  
**Reason**  
代理运行时的价值来自行动闭环；没有行动需求时，它只增加复杂度。  
↓  
**Expected Outcome**  
以更低成本获得答案，避免不必要的系统权限。

## 5. 搜索空间扩展（Search Space Expansion）

初学者通常问：“Codex 能不能做这件事？”  
专家更常问：“在什么上下文、权限、证据与失败模型下，它做这件事才值得信任？”

### 5.1 初学者通常不会想到的问题

#### 关于任务定义

- “修好”是测试通过、用户行为恢复、性能达到阈值，还是仅消除错误？
- 哪些文件可以改，哪些公共接口、数据格式和依赖版本必须保持不变？
- 如果发现根因超出范围，代理应停止、报告，还是扩大任务？
- 什么信息缺失时应先调查，而不是猜测？

#### 关于事实与上下文

- 仓库文档、代码、工单和远程系统发生冲突时，谁是事实来源？
- 会话中的旧结论是否已经被后续代码变化推翻？
- 上下文压缩后，哪些边界或决定可能被丢失？
- 外部网页、Issue 评论或工具返回内容是否可能含有提示注入？
- 代理看到的是完整仓库、稀疏检出、生成文件，还是过期缓存？

#### 关于权限

- 沙箱限制的是文件、进程、网络，还是全部？
- “无需审批”是否只是减少询问，而非扩大技术权限？
- MCP 或连接器的读写动作是否遵循与 Shell 相同的审批逻辑？
- 附加目录、套接字、凭据和本地服务是否偷偷扩大了主工作区边界？
- 谁可以批准越界，批准的是一次动作还是一种长期能力？

#### 关于验证

- 测试是由代理新写的，还是已有的独立断言？二者证明力一样吗？
- 测试通过是否可能因为没有实际运行、选错目录、跳过用例或用了缓存？
- Diff 是否包含生成文件、锁文件或无关格式化噪声？
- 结果能否在干净环境重现？
- 如果部分步骤成功、部分失败，最终状态如何识别和恢复？

#### 关于时间与运营

- 长任务中基线代码变化后，结果还适用吗？
- 恢复会话时，环境、依赖和外部状态是否仍与原来一致？
- 多个代理并行修改同一对象时，谁处理冲突与过期假设？
- 成本、延迟和上下文增长什么时候超过人工处理的收益？
- 任务是可安全重试，还是会重复发送消息、创建 PR 或修改数据？

### 5.2 专家真正关心的问题

| 维度 | 专家问题 | 它决定什么 |
|---|---|---|
| 目标可判定性 | 验收条件能否转化为独立断言？ | “完成”是否可证明 |
| 环境保真度 | 本地或云环境是否代表真实构建与运行环境？ | 结果是否可迁移 |
| 上下文完整性 | 关键代码、策略和外部事实是否可见且新鲜？ | 推理上限 |
| 权限最小化 | 完成任务所需的最小读、写、执行和网络能力是什么？ | 爆炸半径 |
| 动作可逆性 | 是否有 Git 检查点、补偿操作、快照或隔离环境？ | 错误成本 |
| 非确定性管理 | 如何用约束、评测和多样化审查控制结果方差？ | 一致性与规模化 |
| 证据独立性 | 验证机制是否独立于生成者的假设？ | 置信度可信度 |
| 供应链边界 | 依赖安装、脚本、Hooks、MCP 和网页中谁可能不可信？ | 安全模型 |
| 机密生命周期 | 凭据在哪一阶段可见、是否进入日志或子进程？ | 数据泄露风险 |
| 并发与基线 | 多任务是否共享工作区、缓存、分支或远程状态？ | 冲突与污染 |
| 可观察性 | 能否区分计划、调用、接受、完成和生效？ | 故障定位与审计 |
| 失败关闭 | 工具、MCP 或验证不可用时，是停止还是带病继续？ | 自动化可靠性 |
| 配置治理 | 哪些是个人偏好，哪些是项目约定，哪些必须组织强制？ | 可维护性与合规 |
| 经济性 | 哪些步骤应交给强模型，哪些应交给确定性工具？ | 质量、成本、速度 |

### 5.4 下一步值得探索的问题

1. 怎样把自然语言目标变成“任务契约”，而不是步骤清单？
2. 怎样为不同风险等级设计权限预设，而不是每次临时决定？
3. 怎样区分仓库知识、可复用工作流、运行配置和组织政策的正确承载层？
4. 怎样建立独立于代理自述的验证链？
5. 怎样让非交互任务具备稳定输入、结构化输出、超时和失败语义？
6. 怎样在并行代理之间划分工作集，避免共享状态冲突？
7. 怎样评估模型升级是否真的提高任务成功率，而非只提高回答观感？
8. 怎样识别提示注入、恶意仓库脚本和不可信 MCP 的组合风险？
9. 怎样把一次成功任务沉淀为测试、规则、Skill 或确定性自动化？
10. 怎样用真实返工率、缺陷率和交付周期评估 Codex，而不是用代码行数？

### 5.5 决定领域上限的问题

这个领域的上限不由“代理能调用多少工具”决定，而由以下问题决定：

- **目标能否被清晰表达并可机器验证？**
- **组织能否把隐性知识变成可维护的上下文与规则？**
- **执行环境能否复现真实约束？**
- **权限能否细粒度、可审计、默认最小化？**
- **失败是否可被检测、隔离、回滚和学习？**
- **人能否把注意力集中在高价值决策，而不是重新微操每一步？**

## 6. 生态系统（Ecosystem）

### 6.1 Codex 各表面在整体中的位置

~~~mermaid
flowchart LR
    Intent[目标 / Issue / 设计 / 故障] --> Surface{选择执行表面}
    Surface --> CLI[CLI<br/>本机终端与脚本]
    Surface --> IDE[IDE<br/>编辑器上下文]
    Surface --> App[Desktop App<br/>规划、审查与交互]
    Surface --> Cloud[Cloud<br/>隔离、后台、并行]

    Shared[按表面支持范围生效的约束与扩展<br/>AGENTS.md · Config · Skills · Plugins · MCP · Hooks]
    Shared -.提供规则、上下文或工具.-> Surface

    CLI & IDE & App & Cloud --> Repo[Repo / Working Tree]
    CLI & IDE & App & Cloud --> Tools[本地工具 / 外部系统]
    Repo & Tools --> Evidence[Diff / Checks / Review / PR]
    Evidence --> Human[人类验收与责任]
~~~

不同表面不是能力等级，而是工作拓扑：

- **CLI** 靠近本机仓库、Shell 和自动化；
- **IDE** 靠近当前编辑上下文和局部交互；
- **Desktop App** 更适合跨文件规划、审查和可视化协作；
- **Cloud** 更适合隔离、后台、复现和并行。

选择表面的核心不是“哪个更高级”，而是：真实环境在哪里、任务需不需要持续互动、是否需要隔离和并行、结果由谁审查。

这些扩展面并非在所有表面上完全等价：例如 CLI 与 IDE 共享本机配置层，AGENTS.md 可以随仓库为本地或云任务提供指导，而 MCP、Plugins、Hooks 和组织策略的可用范围还取决于产品表面、工作区政策和当前版本。不要把“同一生态”误解为“处处拥有相同权限与行为”。

### 6.2 上游（Upstream）

Codex 的上游决定它为什么行动以及基于什么行动：

- 产品目标、Issue、故障报告和设计决策；
- 代码库、依赖、架构与历史；
- 团队约定、测试策略和发布规则；
- 用户身份、组织政策和风险分类；
- 环境定义、工具链和可访问数据源。

如果上游只给“做得更好”，代理就只能猜什么叫“好”。高质量委托的核心是提供**影响结果的事实与边界**，而不是替 AI 编写每一步操作。

### 6.3 下游（Downstream）

Codex 的下游不是“回答”，而是：

- 候选代码、配置、迁移与文档；
- 本地工作树、提交、PR 和审查发现；
- 构建、测试、静态分析和安全检查；
- CI/CD、发布系统与真实产品行为；
- 机器可消费的报告、结构化数据和自动化决策。

越靠近生产和外部写操作，下游越需要权限分离、明确审批、独立验证和回滚路径。

### 6.4 替代方案（Alternatives）

| 替代方案 | 最擅长 | 相比 Codex 代理的关键差异 |
|---|---|---|
| 人类工程师手工执行 | 价值判断、模糊沟通、跨组织协调 | 适应性强但吞吐与上下文切换成本高 |
| 自动补全 | 当前光标附近的低延迟生成 | 局部，不维护完整执行与验证循环 |
| 普通聊天模型 | 解释、设计讨论、知识问答 | 通常不直接接触真实工作区和执行反馈 |
| 确定性脚本 / CI | 已知路径、稳定输入、严格复现 | 遇到未知异常缺少自适应判断 |
| IDE Agent | 编辑器内局部或项目工作 | 与 CLI 主要差异在交互表面和上下文入口 |
| API / Agent SDK | 在产品中构建定制代理系统 | 可编程性更高，但需自行设计运行时、权限和观测 |
| RPA / Computer Use | 操作只有图形界面的系统 | 更接近像素与界面，通常比代码/协议接口脆弱 |
| Codex Cloud | 后台、隔离、并行、远程委托 | 是同一类代理的另一执行拓扑，不是简单替代品 |

一个重要原则：

> **已知且稳定的步骤交给确定性系统；未知且需要判断的路径交给代理；价值与责任判断保留给人。**

### 6.5 互补方案（Complements）

| 互补系统 | 它补上什么 | 与 Codex 的正确关系 |
|---|---|---|
| Git | 差异、历史、分支与恢复 | 为代理修改提供可审查边界和检查点 |
| 测试与静态分析 | 独立、可重复的行为断言 | 给代理反馈，也给人验收证据 |
| 容器 / 可复现环境 | 隔离依赖和系统状态 | 降低“在我机器上可用”的偏差 |
| AGENTS.md | 仓库级长期指导 | 固化约定、验证命令和禁区；按目录继承 |
| Config / Profiles | 运行默认与场景预设 | 管模型、沙箱、审批、MCP 等运行参数 |
| Skills | 可复用的任务方法 | 把成熟工作流从提示中抽离出来 |
| Plugins | 可分发能力包 | 组合技能、工具连接、Hooks 与资源 |
| MCP / Apps | 外部上下文与动作 | 扩展代理世界，但也扩展信任边界 |
| Hooks / Rules | 生命周期治理与机械约束 | 在关键事件执行一致检查，不依赖模型记忆 |
| Managed Requirements | 组织强制底线 | 限制用户或项目不能绕过的配置 |
| CI/CD | 受控集成与发布 | 把候选修改送入稳定、可审计的交付系统 |
| Observability | 日志、事件、成本与失败信号 | 让自动任务能诊断、审计和改进 |

官方配置模型区分一次性覆盖、项目配置、Profile、用户配置、系统默认与组织要求；这种分层的意义是让“临时选择”“团队默认”和“不可绕过底线”不要混成一团。[Config basics](https://developers.openai.com/codex/config-basic) · [Configuration reference](https://developers.openai.com/codex/config-reference)

## 7. 可迁移原则（Transferable Principles）

### 7.1 第一性原理

1. **代理是反馈控制系统，不是文本生成器。**  
   没有环境观察、动作和反馈，代理只剩回答。

2. **目标、能力、授权、证据必须分离。**  
   想做什么、能做什么、被允许做什么、如何证明做对，是四个不同问题。

3. **真实系统拥有最终解释权。**  
   模型的总结、计划和置信度都不等于文件、测试或业务状态。

4. **上下文质量决定推理上限。**  
   更强模型不能可靠补偿缺失、冲突或被污染的事实。

5. **最小权限应按任务设计，而非按工具品牌设计。**  
   权限应匹配本次所需状态变化，默认不开放无关能力。

6. **非确定性应由约束与评测管理。**  
   不要试图把代理每一步写死；要固定边界、可观察状态和验收断言。

7. **确定性组件应承担确定性工作。**  
   格式化、编译、测试、模式校验和权限强制应尽量由工具完成，而非依赖模型自觉。

8. **自动化会同时放大价值与错误。**  
   并行、无人值守和广泛权限提高吞吐，也会扩大错误速度和半径。

9. **可逆性降低探索成本。**  
   分支、Diff、隔离环境、快照和补偿路径让代理可以安全尝试。

10. **人类责任不会因为操作被代理接管而消失。**  
    AI 可以拥有行动自由度，不应自动拥有目标定义权或最终接受权。

### 7.2 可迁移的方法论

任何代理任务都可以用同一份“七字段任务契约”思考：

| 字段 | 要回答的问题 |
|---|---|
| Outcome | 最终需要出现什么可观察结果？ |
| Source of Truth | 冲突时以哪个系统或文档为准？ |
| Scope | 哪些对象在范围内，哪些明确不在？ |
| Constraints | 兼容性、性能、安全、风格或业务禁区是什么？ |
| Authority | 允许哪些读、写、执行、联网和外部动作？ |
| Evidence | 哪些独立检查足以证明结果？ |
| Stop / Escalate | 遇到什么情况必须停下并请求决策？ |

它比“请按以下 27 个步骤操作”更适合 AI：既给足自由度，又把不可让渡的决定固定下来。

一个可迁移的风险策略是：

> **先缩小世界，再增加自治。**

也就是先限定工作区、数据源、工具和网络，再减少不必要的人工审批。自治不必等于无限权限。

### 7.3 当前实现细节

这些内容有用，但不应成为长期心智模型的核心：

- 某一版本的子命令、旗标拼写和别名；
- 具体模型名称、默认模型和支持的 reasoning effort 枚举；
- 某个平台当前使用的沙箱实现；
- 某种配置文件路径、优先级细节和实验性开关；
- TUI 快捷键、Slash 命令和 UI 入口；
- Cloud 容器镜像、缓存时长和当前网络默认；
- 某个 MCP 服务的认证字段与工具名称。

它们应由官方参考或 AI 在需要时检索，而不是由人长期背诵。

### 7.4 长期稳定的知识

- 目标、范围、约束、事实来源和验收；
- 模型、代理、工具与执行环境的区别；
- 沙箱与审批的正交关系；
- 最小权限、信任边界和爆炸半径；
- 状态、反馈、幂等性、并发、可逆性和部分失败；
- Diff、测试、审查与业务验收的证据层级；
- 确定性自动化与自适应代理的分工；
- 本地、云端、交互和非交互的拓扑选择；
- 人对价值判断、授权和最终采用负责。

### 7.5 容易变化的知识

- 支持的模型、默认值、服务层级与价格；
- 沙箱、网络搜索、自动审批和多代理的具体行为；
- CLI、App、IDE 与 Cloud 之间共享哪些配置；
- Skills、Plugins、MCP、Hooks 的成熟度和分发方式；
- 云环境、认证、缓存和企业策略字段；
- 特定命令和输出事件的格式。

### 7.6 维护本文的规则

- 每次版本更新，先检查“核心控制变量是否变化”，再检查名字；
- 把具体旗标留在官方参考，不在本文复制完整列表；
- 对安全默认、网络、审批和配置优先级使用官方资料复核；
- 示例模型名不写入长期原则；
- 新能力应先回答它改变了“上下文、工具、权限、拓扑还是证据”中的哪一层；
- 新增功能如果不能改变决策，就不必进入心智模型。

## 8. 最小心智模型（Minimum Mental Model）

如果只能记住 16 个概念，请记住这些：

| # | 概念 | 最短解释 |
|---:|---|---|
| 1 | Goal | 代理优化的目标必须由人给定 |
| 2 | Acceptance | “完成”必须有外部可判断标准 |
| 3 | Source of Truth | 冲突时知道该相信谁 |
| 4 | Scope | 明确任务对象与爆炸半径 |
| 5 | Agent Loop | 观察—计划—行动—反馈—修正 |
| 6 | Model | 提供推理能力，但不是代理整体 |
| 7 | Context | 代理当前可见的世界切片 |
| 8 | Workspace | 本地状态和主要读写边界 |
| 9 | Sandbox | 技术上能做什么 |
| 10 | Approval | 什么时候必须停下来问 |
| 11 | Tools | 将推理变成现实动作的接口 |
| 12 | Network Boundary | 开放世界访问同时带来新鲜度和风险 |
| 13 | Diff | 候选变化的可审查表示 |
| 14 | Evidence | 测试、检查、日志和独立审查 |
| 15 | Session / Topology | 本地或云、交互或非交互、继续或分叉 |
| 16 | Human Responsibility | 目标、授权与最终采用不能外包消失 |

把它压缩成一句检查语：

> **谁要把哪些真实对象从什么状态变成什么状态；Codex 能看到什么、能做什么、何时必须问；最终用什么独立证据判断成功，失败后怎样停止或恢复？**

### 最重要参数的稳定优先级

当时间有限时，按以下顺序决定：

1. **目标与验收**：否则优化方向不明；
2. **工作范围与事实来源**：否则可能改错对象；
3. **沙箱、网络与审批**：否则风险半径不明；
4. **验证与恢复**：否则无法可信地接受结果；
5. **上下文与工具**：让代理拥有完成任务所需的世界；
6. **执行拓扑**：决定互动、并行、隔离和持续性；
7. **模型与推理强度**：在前六项清楚后优化质量、速度和成本；
8. **界面偏好与易用性细节**：最后再调。

这解释了为什么“换更强模型”经常没有解决根本问题：真正的瓶颈可能是目标模糊、上下文错误、验证薄弱或权限设计失衡。

## 9. 初学者最容易误解什么？

| 误解 | 为什么会产生 | 更准确的心智模型 |
|---|---|---|
| Codex 是会聊天的代码生成器 | 最显眼的是自然语言回复 | 回复只是控制面；价值来自对真实环境的观察、行动与反馈循环 |
| Codex CLI 就是 ChatGPT 放进终端 | 两者都使用模型与对话 | CLI 更靠近本机仓库、Shell、权限边界和自动化接口 |
| 最重要的是选最强模型 | 模型名称容易比较 | 结果更常由任务契约、上下文、权限和验证共同决定 |
| Prompt 越长越好 | 害怕 AI 漏掉要求 | 应提供改变结果的目标、事实与边界；冗余会挤压注意力并制造冲突 |
| 代理有工具就会正确使用 | 工具调用看起来很专业 | 工具扩展能力，不保证目标、参数、来源或解释正确 |
| 沙箱与审批是一回事 | 两者都在“限制行动” | 沙箱决定技术能力，审批决定介入时机；必须分别设计 |
| never 意味着无限权限 | “从不询问”听起来像全自动 | 它只改变询问策略；实际能力仍由沙箱、工具和组织策略限制 |
| workspace-write 意味着整个机器可写 | “能写”被理解得过宽 | 主要写边界是工作区；附加目录、网络和受保护路径仍是独立边界 |
| AI 说测试通过就等于验证完成 | 自然语言总结流畅且权威 | 应检查真实运行记录、范围、退出结果与必要的独立验证 |
| 测试通过就等于需求完成 | 测试看起来客观 | 测试只证明其覆盖的断言；业务验收仍需回到目标 |
| Diff 小就一定安全 | 小改动容易审查 | 小变化也可能触及高杠杆接口、权限或数据语义 |
| 非交互模式只是少了界面 | 表面差异是有没有 TUI | 它把代理变成流水线组件，要求稳定输入、输出、失败和权限契约 |
| Cloud 只是远程跑得更久 | 只看到后台执行 | Cloud 改变隔离、环境复现、并行、网络与凭据边界 |
| AGENTS.md 是另一个 Prompt | 都包含自然语言要求 | 它是按仓库与目录继承的长期指导层，寿命与作用域不同 |
| Skill 会自动获得更多权限 | Skill 似乎“增加能力” | Skill 主要封装方法；真实行动仍受工具可用性、沙箱和审批控制 |
| MCP 是“给模型加知识” | 常被用于文档检索 | MCP 同时可能提供写动作；它扩展上下文，也扩大行动与信任边界 |
| Resume 后一切和原来一样 | 会话连续让人误以为世界连续 | 消息可恢复，但代码、依赖、网络和远程状态可能已经变化 |
| 自动化越多越专业 | 无人值守看起来成熟 | 只有可观察、可失败关闭、可恢复的自动化才真正成熟 |
| AI 负责操作后人就不必懂系统 | 具体步骤确实可以外包 | 人更需要理解目标、状态、边界、证据与后果，才能正确委托 |

## 10. 总结（Summary）

Codex CLI 的本质不是一组要背诵的命令，而是一种新的软件工作分工：

- 人定义目标、边界、事实来源和验收；
- 模型提供推理能力；
- 代理组织观察、计划、行动和反馈；
- 工具把推理落实到真实系统；
- 沙箱、审批与组织策略限制行动半径；
- Diff、测试、日志与审查提供证据；
- 人基于证据决定接受、纠偏、停止或扩大范围。

如果只保留一个世界模型，请保留这个：

~~~mermaid
flowchart LR
    Intent[意图] --> Contract[任务契约]
    Contract --> Agent[受约束代理]
    Context[上下文] --> Agent
    Authority[权限与审批] -.限制.-> Agent
    Agent --> Action[工具行动]
    Action --> Reality[真实系统状态]
    Reality --> Evidence[独立证据]
    Evidence --> Agent
    Evidence --> Human[人类判断与责任]
~~~

最后完成这句话：

> **我真正获得的不是一套 Codex 命令参数，而是一种把高层意图变成受约束、可观察、可验证的软件状态变化的委托模型。**
